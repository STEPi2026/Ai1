## 1. A5 배포 상태 정정 — 확인

## 2. `problem_type` 자동 판정 규칙 — 조건부 동의

> 제안: `problem_latex` 에 `=` 가 있으면 `equation`, 없으면 `expression`

규칙 자체는 **표현식/방정식 구분용으로 타당**합니다. 다만 세 가지를 계약에 명시해야
합니다.

### 2.1 정규화 목록 (양쪽 동일 적용)

- 전각 `＝` → `=`
- 공백·`\;`·`\,`·`\!` 제거 후 판정
- `\mathrm{=}`, `\text{=}` → `=`
- `\le` / `\leq` / `\ge` / `\neq` 등은 `=` 문자를 포함하지 않으므로 자동 제외
- `\overset{?}{=}` 처럼 `=` 를 포함하는 장식은 **equation** 으로 봅니다(빈칸 채우기)

### 2.2 단일 소유자

- Backend 가 `problem_type` 을 보내면 AI①은 그 값을 **그대로 신뢰**합니다(재판정하지 않음).
- 생략했을 때만 AI①이 같은 규칙을 적용합니다.
- 두 구현이 갈라지지 않도록 규칙 문구는 위 2.1 을 기준으로 고정합니다.

### 2.3 이 규칙의 실제 위험 (AI① 실측)

AI① 파서로 직접 확인한 결과입니다.

| `problem_latex` | `=` | AI① 파싱 | 규칙 판정 | 실제 의미 | 결과 |
|---|---|---|---|---|---|
| `x^2-5x+6=0` | O | `eq` | equation | 방정식 | 정상 |
| `(x+1)(x+2)` | X | `expr` | expression | 전개 | 정상 |
| `f(x)=x^2-5x+6` | O | `eq` | equation | 함수 정의(꼭짓점·그래프) | equation 모드 부적합 가능 |
| `A={1,2,3}` | O | `eq` | equation | 집합 표기 | equation 모드 부적합 |
| `2x+6=` | O | None | equation | OCR 이 우변 유실 | `E_BAD_PROBLEM`(재시도 가능) |
| `\begin{cases} x+y=3 \\ x-y=1 \end{cases}` | O | None | equation | 연립방정식 | 미지원(`E_BAD_PROBLEM`) |

**핵심:** `=` 존재 규칙은 "표현식 vs 방정식" 구분에는 유효합니다. 그러나
**"등식이면 모두 방정식"은 아닙니다.** 함수 표기·집합 표기는 `=` 가 있어도 equation
모드가 맞지 않습니다. 지금 단계에서는 이들을 별도 유형으로 만들지 말고
**P1 범위 밖**으로 두는 것을 제안합니다.

## 3. `E_INVALID_TARGET_FORM` 처리 — 동의

Backend 가 `equation` 에 `target_form` 을 보내지 않으므로 실제로는 나오지 않아야 합니다.
나오면 계약 오류로 기록 + FAILED 처리에 동의합니다.

한 가지만 부탁드립니다: **APP 에 재시도를 유도하지 마세요.** 이 코드는 학생 입력
문제가 아니라 클라이언트/설정 버그 신호입니다. 재시도해도 결과가 같습니다.
(운영 알림 대상으로 두는 편이 맞습니다.)

## 4. `answer_form` 공백과의 관계 — 분리 전송 제안

> Backend 계획: `answer_form` 이 없는 Skill 은 `problem_type` 을 보내지 않는다(현행 equation).

이 계획을 그대로 두면 다음이 발생합니다.

- 표현식 문제인데 `answer_form` 이 비어 있음 → `problem_type` 생략 → 기본 `equation`
  → **`E_NOT_EQUATION` 422**
- 즉 **Seed 94개 `answer_form` 이 채워질 때까지 표현식 문제는 전부 422** 입니다.

**제안: `problem_type` 과 `target_form` 을 분리해서 보냅니다.**

| 상황 | `problem_type` | `target_form` | AI① 동작 |
|---|---|---|---|
| `answer_form` 있음 | `expression` | `expanded` 등 | 동치 + 마지막 줄 형태 검사 |
| `answer_form` **없음** | `expression` | `null` | **동치만** 검사(형태 검사 없음) |
| 방정식 문제 | `equation` 또는 생략 | `null` | 현행 |

`problem_type="expression"` + `target_form=null` 은 **유효한 조합**입니다.
`answer_form` 이 없어도 `problem_type` 은 보낼 수 있습니다. 이렇게 하면 콘텐츠 작업을
기다리지 않고 표현식 문제의 **동치 판정**부터 켤 수 있습니다.

## 5. 안전장치 3개 (제안)

| # | 규칙 | 이유 |
|---|---|---|
| S1 | equation 모드인데 문제 파싱이 `expr` → `E_NOT_EQUATION` | 이미 합의. fail-closed |
| S2 | expression 모드인데 **풀이 줄이 `eq`** 로 파싱 → 판정하지 않고 `REVIEW_REQUIRED` | 문제를 표현식으로 봤는데 학생이 등식으로 썼다면 **유형 오분류 가능성**이 높습니다. 조용히 true/false 를 내면 오판이 저장됩니다 |
| S3 | 함수 표기(`f(x)=`, `y=`)·집합 표기(`A={...}`)·연립(`\begin{cases}`)은 P1 범위 밖 | 별도 유형을 만들지 않고 `E_UNVERIFIABLE`/`REVIEW_REQUIRED` 로 떨어지게 둡니다 |

S2 는 `=` 규칙의 오분류를 **조용한 오판으로 바꾸지 않기 위한 장치**입니다.
Backend 추가 부담은 없고(응답 `analysis_status` 만 봄), AI① 쪽에서 처리합니다.

## 6. `correct: null`

Backend 응답에 이미 `status`(REVIEW_REQUIRED 포함)와 `is_correct`(null 가능)가 있다는 점

## 9. 추가: 항등식 오탐 수정 (A-1, 코드 반영 완료)

A6 초안의 근거로 언급했던 **항등식 오탐 중 줄↔줄 부분은 이미 수정**했습니다.
(계약 협의와 별개로 진행한 버그 수정입니다.)

| 입력 | 수정 전 | 수정 후 |
|---|---|---|
| `5x-3=5x-3`(항등식) vs `5x-3=5x-2`(모순) | `True` (오탐) | **`False`** |
| `(x+1)(x+2)=x^2+3x+2` vs `=x^2+3x+1` | `True` (오탐) | **`False`** |
| `x^2-5x+6=0` vs `(x-2)(x-3)=0` | `True` | `True` (불변) |
| `x^2-5x+6=0` vs `(x-2)(x-4)=0` | `False` | `False` (불변) |

원인은 SymPy `solve()`가 **항등식**과 **모순**을 모두 빈 해 집합으로 돌려주는 것입니다.
두 경우를 구분해 "항등식 ↔ 모순"만 비동치로 확정했습니다.

**남은 한계:** 문제식 자체가 모순인 경우(`(x+1)(x+2)=x^2+3x+1` → `True`)는 그대로입니다.
이것이 A6 §3.4의 `REVIEW_REQUIRED` 분기가 처리할 잔여분입니다. 계약 필드 변경은 없습니다.
서버 재시작 전이므로 실행 중 서버에는 아직 반영되지 않았습니다.
