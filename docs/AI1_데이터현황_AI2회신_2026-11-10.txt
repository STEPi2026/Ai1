AI② 담당자님께

AI① Learning Intelligence의 데이터 확보·구현 현황과 Backend DB 적재 협의 의견을 정리했습니다.
기준일은 2026-11-10이고, 근거는 현재 저장소 코드(app/, data/, tests/, eval/)와
Backend에서 받은 시드 자료(Concept 42 / Skill 94 / 문제 94 / 선수관계 92 / 오개념 23)입니다.

이 문서는 "AI①이 무엇을 실제로 갖고 있고, 무엇이 아직 없는지"를 먼저 구분한 뒤,
OCR 평가용 원본 데이터와 서비스 DB 데이터를 분리해 정리했습니다.


======================================================================
0. 한 줄 결론
======================================================================

- AI①은 지금 "텍스트 등식 풀이 분석기"로 동작합니다. 문제/풀이 이미지를 직접 나누거나
  LaTeX로 바꾸는 기능은 아직 없고, Google Vision을 쓰는 OCR 경로도 "원문 텍스트 미리보기"
  수준입니다.
- 실제 학생 문제 이미지·정답 전사문·인쇄/손글씨/품질별 OCR 평가 데이터는 현재 0건입니다.
  저장소에 있는 것은 계약·회귀용 합성 fixture뿐입니다.
- 서비스에 넣을 데이터(문제·정답 풀이·분석 결과·학생 상태)는 Backend MySQL이 소유하고,
  AI①은 DB 없이 요청을 받아 결과 JSON만 반환하는 현재 구조를 유지하는 것이 맞습니다.
- OCR 학습·평가용 원본 데이터는 서비스 DB에 넣지 말고 eval 전용 저장소(로컬/오브젝트 스토리지)에
  분리해야 합니다. 벤더 OCR을 쓴다면 이 데이터는 "학습"이 아니라 "평가·검증"용입니다.
- 당장 막는 것은 ① 실제 OCR 평가셋 ② Skill/MIS 공식 코드 승인 ③ problem_code ↔ problem_id
  규칙 ④ 94개 문제의 정답·정답 풀이입니다.

[4] OCR 인식 성공·실패·불확실 사례
  - [확보/계약] 상태 파생 규칙은 구현돼 있습니다.
      COMPLETE  : 문제·풀이 단계가 읽혔고 unreadable 항목이 없음
      PARTIAL   : 일부만 읽힘(문제/풀이 미분리, unreadable 존재)
      UNREADABLE: 읽을 수 있는 내용이 하나도 없음
  - [계약만] 합성 handoff 9건이 성공/부분/실패/스킵/UNKNOWN을 나눠 커버합니다.
  - [미확보] 실제 OCR 성공·실패·불확실 사례는 0건입니다.
  - [미구현] OCR 전용 TIMEOUT/FAILED 상태 코드, 재시도 결과 동일성, 신뢰도 보정(calibration)은
      아직 없습니다.

[5] OCR 엔진 연결 상태
  - Google Cloud Vision DOCUMENT_TEXT_DETECTION provider가 opt-in으로 연결돼 있습니다.
      AI1_OCR_PROVIDER=google_vision 일 때만 선택
      미설정 시 503 E_OCR_NOT_CONFIGURED
  - 하지만 실제 Vision API 호출은 0회입니다. billing/credential/무료 quota 확인 전에는
      호출하지 않는 상태입니다.
  - Mathpix는 eval 하네스(eval/mathpix_*.py)만 있고 서비스에는 연결되지 않았습니다.
      선행 조건 5개(계정/키, 예산, improve_mathpix opt-out 확인, 실제 이미지 20장+라벨,
      Backend presigned URL)가 모두 미충족입니다.
  - 즉 현재 OCR은 "사진에서 글자를 읽어 원문을 보여주는 미리보기"이지,
    "문제/풀이를 구조화해 분석까지 자동 연결하는 OCR"이 아닙니다.

----------------------------------------------------------------------
1-3. Backend 연동용 데이터
----------------------------------------------------------------------

[1] 기존 Seed의 problem_code, skill_id, misconception 코드 매핑
  - [미확정] AI①에는 problem_code 개념이 없습니다.
      AI①은 problem_id를 "불투명 문자열"로만 보존합니다.
      · PRB-000123 같은 Seed 문제 코드
      · CAPTURED-{촬영문제ID}-{문제식 해시}
      둘을 추측하거나 합치지 않습니다.
      Backend Q5(시드 problem_id를 problems.problem_code로 쓸지)도 아직 미결정입니다.
  - [부분] Skill: 내부 skill_id(예: distribution)와 Backend SKL 코드는 다릅니다.
      현재 승인 1건 + 후보 15건(그룹 노드 2건 제외) + 대응 없음 10건.
  - [부분] Misconception: 내부 19개와 Backend 23개가 다릅니다.
      현재 승인 1건 + 후보 2건 + 대응 없음 16건.
      Backend Seed 23개는 전부 다항식(STP-1-001~011) 계열이라
      AI①의 방정식·부등식·집합·명제 오개념과 겹치지 않습니다.
  - [확정] Concept(STP)은 AI①이 만들지 않습니다.
      Backend가 공식 Skill-Concept 관계로 도출합니다.
      AI① 응답에는 concept_id/STP 코드가 없습니다.

[2] AI① 분석 결과의 요청·응답 필드
  - 요청: POST /api/v1/attempts/{attempt_id}/analyze
      problem_id, problem_latex, problem_skills[], student_id, solution_text,
      correct_solution(선택), engine(rule|bkt),
      problem_question_text, problem_concept_name, problem_unit_name
      → 10개 필드, extra="forbid" (모르는 필드는 422)
  - 응답: 31개 필드
      식별/상태: analysis_id, attempt_id, problem_id, student_id, analysis_status,
                 analysis_count, attempted_at
      결과: correct, error_step, first_error_step_index, error_type, error_subtype,
            skill, state, mastery, misconception_id, confidence
      단계: steps_latex[], valid[], unrecognized[], step_list[]
      다중 오류/관측: errors[], observations[], misconception_tags[],
                      states{}, mastery_by_skill{}
      Backend 코드: misconception_tag, official_skill_codes[],
                     official_misconception_codes[], provisional_skill_codes[],
                     provisional_misconception_codes[]
  - Legacy POST /analyze-solution은 16개 필드로 별도 계약입니다.
      새 Backend 연동에는 Attempt API를 쓰고 Legacy는 건드리지 않는 것이 원칙입니다.

[3] 문제 이미지 및 분석 결과의 연결 관계
  - [Backend 소유] 원본 이미지 저장·보관은 Backend 책임입니다.
      AI①은 이미지 bytes를 받지 않고 image_reference(HTTPS URL)만 받습니다.
  - [현재] 이미지와 분석을 잇는 키는 attempt_id 하나입니다.
      OCR 결과 ID는 {attempt_id}#ocr-p{page_index} 형태로 파생되지만,
      OCR 결과를 AI①이 저장하지 않으므로 분석 요청에 자동으로 붙지 않습니다.
      Backend가 OCR 원문을 확인·보정한 뒤 solution_text와 problem_latex를 만들어
      /analyze에 보내는 2단계 구조입니다.
  - [미구현] image_id, ocr_result_id, analysis_id를 한 번에 잇는 FK는 AI①에 없습니다.
      Backend가 attempts.solution_image_url + ai_analysis_results.attempt_id로 연결해야 합니다.
  - [확정] AI①은 OCR 호출만으로 Knowledge State를 갱신하거나 Attempt를 저장하지 않습니다.

[4] AI②가 진단에 활용할 수 있는 오류 분석 정보
  - 사용 가능:
      analysis_status (ANALYZED / REVIEW_REQUIRED / UNKNOWN)
      first_error_step_index / error_step (1-based)
      error_type / error_subtype
      skill (관측된 대표 Skill — 문제 선언 Skill과 다를 수 있음)
      errors[].step_no, ref_step_no, ref_solution_step_no
      errors[].skill_ids, misconceptions_ids
      errors[].evidence_latex, description_ko, confidence
      misconception_tag(단수), misconception_tags[](복수)
      step_list[]: is_correct, status, skill_ids, unrecognized, aligned_solution_step_no
      observations[], states{}, mastery_by_skill{}
      official_skill_codes[], official_misconception_codes[]
  - 사용 시 주의:
      AI①의 mastery/state는 로컬 Rule/BKT 결과입니다. 최종 Student State와

      ai_analysis_id / attempt_id로 조회해야 합니다.
  - 현재 AI②에 직접 못 주는 것:
      overall_confidence 병합값

3. 데이터 구분: OCR 학습·평가용 vs 서비스 DB
======================================================================

[원칙]

[구분표]

  A. OCR 학습·평가용 원본 데이터
     - 대상: 문제 사진, 정답 전사문/LaTeX, 단계 경계 라벨, 인쇄/손글씨 라벨,

     - 저장: eval/_local/ (gitignore) 또는 별도 오브젝트 스토리지
     - 서비스 DB: 넣지 않음
     - AI① runtime: 사용하지 않음 (오프라인 평가에서만 사용)
     - 개인정보: 학생 이름·학번 등 PII 제거, 이미지 hash로 관리

     - 재시작 시 소멸. 멀티워커 멱등성은 Backend unique 제약으로 보완 필요

  E. OCR 호출 예산 원장
     - 대상: Vision 호출 횟수 카운터
     - 저장: 로컬 파일(eval/_local/google_vision/call_log.jsonl)

  "problem_skills": ["SKL-1-004"],
  "student_id": "4821",
  "solution_text": "2(x-3)=6\n2x-3=6\n2x=9\nx=4.5",
  "correct_solution": {
    "solution_id": "SOL-PRB-000123-1",
    "steps": [
      {"latex_text": "2(x-3)=6", "skill_ids": ["linear_equation"]},
      {"latex_text": "2x-6=6", "skill_ids": ["linear_equation"]},
      {"latex_text": "2x=12", "skill_ids": ["linear_equation"]},
      {"latex_text": "x=6", "skill_ids": ["linear_equation"]}
    ],
    "answer_latex": "x=6",
    "is_primary": true
  },
  "engine": "rule",
  "problem_question_text": "다음 방정식을 풀어라. 2(x-3)=6",
  "problem_concept_name": "일차방정식의 풀이",
  "problem_unit_name": "방정식과 부등식"
}

필드 규칙:
  - problem_id: Backend가 정한 불투명 문자열. AI①은 의미를 해석하지 않음.
  - problem_latex: 문제식. 현재는 등식만 지원. 등식이 아니면 E_NOT_EQUATION(422).
  - problem_skills: 내부 skill_id 또는 crosswalk에 있는 SKL 코드.
      · tracking Skill 최소 1개 필요. 없으면 422 E_SKILL_NOT_TRACKABLE.
      · 모르는 SKL 코드는 422 E_UNKNOWN_SKILL_CODE. 기본 Skill로 치환하지 않음.
      · group node는 함께 보내도 되지만 Knowledge State 관측 대상은 아님.
  - student_id: 문자열 또는 정수. 정수는 십진 문자열로 정규화. bool 거절.
  - solution_text: 학생 풀이 원문. OCR 경로에서는 학생이 확인·보정한 텍스트.
  - correct_solution: 선택. 없으면 단계 정렬 없이 분석.
  - engine: rule(기본) 또는 bkt.
  - 표시 메타데이터 3개는 최초 문제 등록 시에만 저장. 저장본이 있으면 무시.

  - official_*: Backend 승인 코드만. 미매핑은 빈 배열.
  - provisional_*: 미승인 후보만. 현재 비어 있음.
  - errors[]: 독립 오류 목록. 연쇄 오류는 내부 suppressed_downstream_steps로 보류.
  - observations[]: Knowledge Observation. outcome은 이진(correct/incorrect).

OCR 계약:

  - OCR confidence와 분석 confidence는 이름·의미 모두 분리.

6-4. 오류 응답 형식
----------------------------------------------------------------------

{
  "detail": {
    "code": "E_UNRECOGNIZED",
    "message": "모든 풀이 단계를 인식하지 못했습니다. 직접 입력으로 다시 시도해 주세요.",
    "analysis_status": "UNKNOWN"
  }
}

  - 분석 불가(E_UNRECOGNIZED / E_UNVERIFIABLE)는 422 + analysis_status=UNKNOWN.
    오답으로 저장하지 않고, Knowledge State도 갱신하지 않습니다.
  - 인증: 401 E_AUTH_INVALID_KEY, 서버 키 미설정: 503 E_AUTH_NOT_CONFIGURED.
  - OCR: 503 E_OCR_NOT_CONFIGURED, 502 E_OCR_PROVIDER_ERROR,
    429 E_OCR_USAGE_LIMIT_REACHED, 422 E_OCR_IMAGE_FETCH_FAILED /
    E_OCR_UNSUPPORTED_IMAGE.
  - 입력 초과: 413 E_INPUT_TOO_LARGE.
  - 파싱 실패: 422 E_BAD_PROBLEM, 비등식: 422 E_NOT_EQUATION.

6-5. DB 적재 시 필드 대응
----------------------------------------------------------------------

  attempts.is_correct              ← analysis.correct
  attempts.solution_image_url      ← Backend 저장 URL (AI① 미전달)
  attempts.hint_count / solve_time ← AI① 입력 아님(Backend 소유)
  ai_analysis_results.first_error_step ← analysis.first_error_step_index (1-based)
  ai_analysis_results.mastery_score    ← analysis.mastery (0~1)
  ai_analysis_results.confidence       ← analysis.confidence
  ai_analysis_results.raw_result       ← 분석 응답 전체 JSON (31필드)
  ai_analysis_results.attempt_id       ← analysis.attempt_id
  ai_analysis_results.misconception_id ← official_misconception_codes의 승인 코드만
                                          (내부 ID를 직접 FK로 쓰지 않음)
  student_states.mastery_score         ← Backend 최종 mastery
  student_states.knowledge_state       ← Backend 최종 state
  student_states.weakness_score        ← 1 - mastery (Backend 계산)
  student_misconceptions.confidence    ← analysis.confidence
  student_misconceptions.detected_at   ← Backend 기록 시각
  tutor_actions.ai_analysis_id         ← AI②가 참조하는 FK

  주의:
    - AI①의 state/mastery는 로컬 값입니다. Backend가 최종 상태를 덮어쓰는 구조가 맞습니다.
    - AI①은 student_states/student_misconceptions에 직접 쓰지 않습니다.
    - 내부 MIS ID(예: 3.1)를 Backend FK에 직접 넣지 않습니다.
      승인된 official_misconception_codes만 FK 후보입니다.
    - 미매핑 MIS는 raw_result에만 남기고, FK에는 넣지 않습니다.

7. 충돌 방지 체크리스트 (기존 Seed와 맞추기)
======================================================================

[1] taxonomy는 frozen
  - data/skills.json, error_types.json, misconceptions.json의 ID를 바꾸지 않습니다.
  - Backend Seed의 ID/코드도 AI①이 임의로 바꾸지 않습니다.
  - 새 의미가 필요하면 "매핑 계층"을 추가합니다.

[2] Skill↔Concept는 매핑 테이블로
  - concepts 42개를 AI① taxonomy에 복제하지 않습니다.
  - skill_concept_map(skill_id, concept_id, source) 형태로 연결합니다.
  - 이름 유사성·Skill 순서·unit 값으로 concept_id를 추측하지 않습니다.
  - problem_concepts를 problem_skills에서 자동 생성하지 않습니다.
  - 하나의 Skill mastery를 여러 Concept에 복제하지 않습니다.

[3] 코드는 Seed에 있는 것만
  - official_*에는 Backend 승인 코드만 넣습니다.
  - provisional_*에도 시드 밖 코드는 넣지 않습니다.
  - SKL-2-037, MIS-2-001/002는 관계자료 xlsx에만 있으므로
    Seed 편입 결정 전에는 내보내지 않습니다.
  - MIS-2-003(일반 계산 실수)은 자동 부여하지 않습니다.
  - MIS-2-004(0으로 나누기)는 detector가 없으므로 코드가 나오지 않습니다.
  - STP-*는 AI①이 만들지 않습니다. Backend가 SKL에서 도출합니다.

[4] problem_code는 명시적으로
  - AI①은 problem_id를 불투명 문자열로만 보관합니다.
  - problem_code(PRB-*)와 내부 problem_id를 이름·해시로 추측해 합치지 않습니다.
  - Backend가 둘의 관계를 표로 관리하거나, 처음부터 같은 값을 보냅니다.

[5] 1:N은 리스트로
  - Skill 1개 ↔ SKL 여러 개는 official_skill_codes[]에 전부 넣습니다.
  - 대표 1개로 줄이지 않습니다.
  - 미매핑은 항목 생략(빈 배열)이며 null 원소를 넣지 않습니다.

[6] 상태·약점 소유권
  - 최종 Student State, weakness_score는 Backend 소유입니다.
  - weakness_score = 1 - mastery로 Backend가 계산합니다.
  - AI①은 mastery/state/observations를 참고값으로만 제공합니다.

[7] 재촬영·재시도
  - 재촬영은 새 attempt_id를 사용합니다.
  - 회차 연결(parent_attempt_id)은 Backend가 저장합니다.
  - AI① 요청 스키마에는 parent_attempt_id가 없습니다.
  - 같은 attempt_id + 같은 본문은 멱등, 다른 본문은 409입니다.

[8] 이미지·개인정보
  - AI①은 이미지 bytes를 받지 않고, 서명 URL만 읽습니다.
  - 이미지 원본·서명 URL·원문을 AI①이 저장하지 않습니다.
  - OCR 원본/라벨은 eval 전용 저장소에 두고 서비스 DB에 넣지 않습니다.
  - 학생 데이터를 AI① 디스크/DB에 저장하지 않습니다.

[9] 계약 필드
  - 기존 11개 필드(correct, error_step, error_type, skill, state, mastery,
    misconception_id, confidence, steps_latex, valid, unrecognized)는 삭제·개명하지 않습니다.
  - 새 값은 additive 필드로만 추가합니다.
  - AnalyzeAttemptRequest는 extra="forbid"이므로 새 요청 필드는
    analyze() 경로까지 함께 내려야 합니다(조용히 무시 금지).

[10] 신뢰도
  - OCR confidence와 분석 confidence를 섞지 않습니다.
  - overall_confidence 병합은 아직 미정입니다.
  - confidence는 "정답 확률"이 아니라 "분류 신뢰도"입니다.

[11] API prefix
  - 신규 API는 /api/v1/...을 사용합니다.
  - Legacy /analyze-solution은 별도 계약으로 유지합니다.
  - /health만 인증 예외입니다.

8. 권장 적재 순서
======================================================================

Step 0. 동결
  - AI① taxonomy ID, Backend Seed ID, 기존 응답 11필드를 동결합니다.
  - 이 단계에서 데이터를 넣지 않고, 매핑표만 설계합니다.

Step 1. Backend 기준정보 적재(기존 Seed 유지)
  - Concept 42 / Skill 94 / 문제 94 / 선수관계 92 / Misconception 23을 그대로 둡니다.
  - AI① taxonomy를 Backend Seed에 맞춰 이름을 바꾸지 않습니다.

Step 2. 매핑 테이블 적재
  - skill ↔ SKL 코드(승인/후보 분리)
  - misconception ↔ MIS 코드(승인/후보 분리)
  - skill ↔ concept(skill_concept_map)
  - problem_code ↔ problem_id
  - 각 행에 source(공식 자료 출처)를 기록합니다.
  - 승인되지 않은 행은 status=CANDIDATE로 두고 official_*에 넣지 않습니다.

Step 3. 문제·정답 데이터 적재
  - 94개 문제의 question, answer, problem_type, difficulty 등은 Backend가 소유.
  - 정답 풀이 94건(가능하면 대안 풀이 추가)을 적재합니다.
  - problem_concepts는 공식 매핑만 명시 적재합니다.
  - AI①에는 문제은행을 복제하지 않고, 요청 시 필요한 문제식·정답 풀이만 전달합니다.

Step 4. 이미지·Attempt 적재
  - 원본 이미지는 Backend 스토리지에 저장하고 attempts.solution_image_url로 연결합니다.
  - AI①은 presigned URL만 받아 OCR 경로에 사용합니다.
  - OCR 결과는 AI①에 저장하지 않고, Backend가 원문 확인·보정 후 /analyze로 보냅니다.

Step 5. 분석 결과 적재
  - ai_analysis_results.raw_result에 AI① 응답 전체(31필드)를 저장합니다.
  - first_error_step, mastery_score, confidence, attempt_id를 함께 저장합니다.
  - misconception_id FK는 official_misconception_codes의 승인 코드만 사용합니다.
  - student_states/student_misconceptions는 Backend 최종 정책으로 갱신합니다.

Step 6. 평가 데이터는 별도 관리
  - OCR 이미지·라벨·벤더 원본 응답은 eval/_local/ 또는 별도 오브젝트 스토리지.
  - 서비스 DB에는 dataset_id, version, image_hash, label_hash, storage_uri 정도의
    메타데이터만 둘 수 있습니다(필요 시 별도 eval 스키마).
  - 학생 PII는 저장하지 않습니다.

10. AI②에 바로 전달할 요약
======================================================================

AI②가 AI① 분석 결과를 진단에 쓰려면, Backend의 ai_analysis_id로 아래 값을 조회하면 됩니다.

  - analysis_status
  - first_error_step_index (1-based)
  - error_type / error_subtype
  - skill (관측 대표 Skill)
  - errors[].step_no / skill_ids / misconception_ids / evidence_latex /
    description_ko / confidence
  - misconception_tag / misconception_tags
  - step_list[].is_correct / status / skill_ids / aligned_solution_step_no
  - official_skill_codes / official_misconception_codes
  - states / mastery_by_skill

AI②가 쓰면 안 되는 값:
  - AI①의 mastery/state를 최종 Student State로 사용
  - 내부 MIS ID(2.1, 3.1 등)를 Backend FK로 직접 사용
  - official_*가 빈 배열인 것을 "오류 없음"으로 해석
  - correct=true를 "완전한 정답 증명"으로 해석
  - OCR confidence와 분석 confidence를 같은 값으로 사용
  - 이미지 원본/서명 URL을 AI① 응답에서 찾기

AI②에 아직 없는 것:
  - overall_confidence 병합값
  - suppressed_downstream_steps
  - concept_id/STP
  - 최종 정답 대조 결과
  - confidence calibration


======================================================================
11. 결론
======================================================================

AI①은 "텍스트 등식 풀이 분석"은 지금도 사용할 수 있습니다.
하지만 "문제집 사진을 찍으면 문제/풀이를 나눠 LaTeX로 바꾸고, 그대로 분석까지" 하는
E2E 이미지 경로는 아직 완성되지 않았습니다. 현재 OCR은 Google Vision 원문 미리보기이고,
실제 이미지·라벨·실호출은 0건입니다.

따라서 다음 순서를 제안합니다.

  1) OCR 평가셋 20~40장 + 라벨을 먼저 확보하고, Google Vision/Mathpix 중 하나를 결정한다.
  2) Backend Seed는 그대로 두고, Skill/MIS/Concept/Problem 매핑 테이블만 추가한다.
  3) 94개 문제의 정답 풀이를 Backend에 적재하고, AI①은 요청으로만 받는다.
  4) 분석 결과는 ai_analysis_results.raw_result + FK로 Backend에 적재한다.
  5) OCR 원본·라벨·벤더 응답은 서비스 DB가 아니라 eval 전용 저장소에 둔다.
  6) AI②는 Backend의 ai_analysis_id로 조회하고, AI① mastery를 최종 상태로 쓰지 않는다.

이 순서면 기존 Seed 코드와 충돌하지 않고, AI①은 별도 DB 없이 현재 구조를 유지할 수 있습니다.

문의나 승인 요청이 필요한 항목은 9장의 우선순위 순서로 회신해 주시면,
AI① 쪽 코드·문서 반영 순서를 맞추겠습니다.
